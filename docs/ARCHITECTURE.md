# Scopeproof architecture

## System overview

Scopeproof combines a private Cloudflare-hosted evidence console with a local macOS capture application.

> **Hosting transition:** the production target is now the AWS-only bridge architecture in [AWS multi-tenant hosting](AWS_MULTI_TENANT_HOSTING.md), using explicit Route 53 tenant hostnames, Cognito, AWS-managed compute/data services, and per-tenant S3/KMS/IAM evidence boundaries. Its operational sequence and unresolved risks are in the [AWS platform runbook](AWS_PLATFORM_RUNBOOK.md) and [AWS adversarial security review](AWS_SECURITY_REVIEW.md). The components below describe the current single-tenant legacy runtime and remain authoritative until the staged migration and isolation gates are complete. No AWS resource described by this repository has been deployed.

## Trust boundaries

1. **User and browser → private Sites application:** the private Sites dispatcher strips untrusted identity headers and supplies authenticated values. The legacy runtime starts only with the explicit single-tenant acknowledgement and consumes identity headers on exactly one configured canonical origin. It requires an active invitation-created membership after the single bootstrap claim, enforces server-side capabilities, and requires same-origin proof for mutations. Direct Worker/preview origins are not trusted web entry points.
2. **Worker → provider and scanner APIs:** hosted secrets authorize bounded evidence reads. Provider data is untrusted input. Every screenshot crosses a separate image-safety boundary through one clean HTTPS endpoint on an exact allowlist; the request binds the complete PNG digest and the response must return that digest plus a valid policy. Recognized OCR text is processed transiently and is not stored. Scanner unavailability, sensitive content, or a response-contract mismatch rejects the screenshot before persistence.
3. **Worker → D1/R2:** D1 holds metadata and digests; R2 holds ciphertext. Encryption uses artifact-specific IVs and authenticated associated data.
4. **macOS screen → Scopeproof Capture:** ScreenCaptureKit provides pixels only after macOS permission and an explicit user action. Unreviewed pixels stay in memory; local OCR covers source pixels, the rendered header, and the exact final encoded artifact before persistence.
5. **Browser → native Local Console:** an ephemeral launch URL places a one-time nonce in the fragment. The bootstrap page exchanges it once with the `Scopeproof-Launch` authorization scheme, clears the fragment, and keeps the returned short-lived bearer in memory. The fragment is not sent with the initial HTTP request and no localhost authentication cookie is created. The server binds only to `127.0.0.1`, requires the bearer for protected requests, validates the exact Host/Origin/Fetch Metadata boundary, accepts no filesystem paths or S3 keys, and resolves artifacts exclusively by validated evidence ID inside the active tenant/workspace root. Switching identity stops the old console and invalidates that browser session. The server—not JavaScript—resolves credentials through the configured in-memory/Keychain provider and reads the matching verified S3 destination binding. A local/S3 join requires a receipt binding exact keys, versions, ETags, checksums, account, settings, tenant/workspace, and local manifest digest. An S3 preview first validates the paired exact-version manifest, then the exact PNG digest, is limited to 40 MiB, and is removed from private temporary storage. A self-consistent S3-only pair remains unverified provenance.
6. **Mac → native upload endpoint:** a 30-day revocable/rotatable bearer token identifies the device and HMAC-authenticates the exact manifest/image digest pair. Schema 7 additionally signs the canonical manifest with the device's ECDSA P-256 provenance key and supplies the next monotonic chain sequence, previous hash, and event hash. The active device owner must still be an active member with collection permission. The server derives metadata only from the signed manifest; validates PNG structure, decompression bounds, dimensions, digest, capture age, session ownership/scope, provenance signature, and exact chain successor; runs the independent image-safety scan; and obtains a trusted RFC 3161 result before any artifact is stored. It reserves then atomically finalizes the device chain and immutable native-manifest link. Records lacking that final link or matching safety receipt remain quarantined from content reads, approval, packages, and Jira.
7. **Scopeproof → assessor/Jira:** exports leave the system through an operator-controlled handoff. Hashes, signatures, visible stamps, and package instructions support independent verification, but destination authorization remains an organizational responsibility.
8. **Scopeproof → Atlassian:** the hosted service exchanges OAuth codes, encrypts rotating tokens with a Jira-specific key, resolves the consented cloud ID, and calls only `api.atlassian.com`. A user/device may access only its own connection and configured project allowlist. The Mac sends approved evidence to Scopeproof, never Atlassian credentials.
9. **Worker → GitHub repository archive:** managed mode accepts a repository only from the configured organization. One-time mode accepts only an exact HTTPS `github.com/owner/repository` URL and a request-scoped token. Both resolve the requested ref through `api.github.com` and follow an archive redirect only to `codeload.github.com`. The archive and every selected manifest are attacker-controlled. The Worker applies byte, entry, decompression-ratio, manifest, UTF-8, and component limits and parses recognized lockfiles without executing repository content. One-time tokens are never persisted or included in audit details.
10. **Mac → AWS STS/S3:** production configuration resolves the caller account through STS, verifies same-account bucket posture, and binds that exact configuration plus the active tenant/workspace in Keychain. Every S3 object path begins with `<configured-prefix>/tenants/<tenant>/workspaces/<workspace>/`. The app generates only regional S3/STS or FIPS endpoints, rejects redirects, and signs expected-owner requests with SigV4. New buckets can receive Block Public Access, ownership enforcement, KMS/DSSE, an SSE-KMS Bucket Key, Object Lock, the exact transport/encryption/deletion-deny policy, Deep Archive, and replication configuration. PUTs require returned SHA-256, encryption, KMS key, and version IDs. The Local Console and native browser use `ListObjectVersions` only beneath the tenant-scoped verified prefix; duplicate versions collapse to one screenshot card with a version count. Explicit PNG/JSON downloads bind the version and ETag, validate content/checksum/size, receive quarantine metadata, and commit atomically from a private temporary file. Before local expiry cleanup relies on the remote copy, live `HEAD` and Object Lock retention calls verify every exact receipt version, checksum, ETag, KMS setting, and future COMPLIANCE retention. Compatible S3 accepts a long-lived key only as an explicit migration mode; the documented exception constrains a dedicated principal to one bucket/prefix and S3-mediated KMS context.
11. **GitHub Release → Mac tester:** the development-preview DMG and adjacent checksum are public distribution inputs. The operator must verify both came from the intended release and that the digest matches before installation. This detects altered bytes but, because the preview is ad-hoc signed and not notarized, does not create an Apple-trusted publisher boundary. Production distribution instead requires Developer ID signing, notarization, stapling, and the signed update-manifest verification path. Before extraction, the production client cross-checks central/local names, flags, compression methods, and payload ranges and validates bounded ordinary-file paths and sizes plus compression ratios; it rejects encrypted, split/ZIP64, unsafe/ambiguous-path, duplicate-offset, symbolic-link, and special-file archives. It allows at most 10,000 entries, 1,024 UTF-8 path bytes per entry, 512 MiB uncompressed per file, 1 GiB uncompressed total, and a 200:1 per-entry and aggregate compression ratio. A post-extraction walk repeats the count, type, and size limits and rejects hard links. The extraction volume must report the declared expanded total plus 256 MiB free, while every release subprocess is limited to 180 seconds and 1 MiB per output stream. Unknown/insufficient capacity, cancellation, timeout, excess output, or validation failure stops the operation before a verified update is saved.
12. **Operator-selected catalog file → Mac:** imported JSON, OSCAL, and CSV data is untrusted input. The app accepts only a regular file up to 5 MB, normalizes bounded metadata, rejects empty or duplicate control identifiers, and records a SHA-256 provenance digest. File selection is explicit authorization to use the catalog for future classification, not proof that the publisher issued it; existing evidence remains immutable.

## Native capture data flow

1. The operator selects a window, scrolling evidence sequence, URL, or display and supplies control context, including an optional page URL. **Capture Frontmost Browser Window** asks a fixed allowlist of browser bundle IDs for the active tab address only after an explicit action and prefills it for confirmation. Failure clears the per-capture URL instead of falling back to stale context. **Open URL & Capture** makes its opened URL authoritative; other capture modes use the operator-confirmed value.
2. ScreenCaptureKit captures pixels into process memory; unreviewed pixels are never written to a temporary file. For scrolling evidence, the operator advances the selected browser window and Scopeproof composes 2–8 equal-sized viewports with explicit numbered dividers. It never performs heuristic overlap deletion, and cancellation or failure discards every intermediate frame.
3. Vision OCR detects supported PAN/credential patterns and masks detected rectangles in memory.
4. For browser-window workflows, Scopeproof captures the right-side live menu-bar region from the same display through ScreenCaptureKit and places those pixels across the top. Full-display capture already contains the real menu bar. The menu-bar pixels receive the same OCR, automatic-redaction, manual-review, and exact-PNG treatment as the evidence source.
5. Scopeproof adds a header above the redacted evidence pixels with only the source origin. Before rendering, indexing, logging, or manifest creation, it removes URL user information, path, query, and fragment in full. A separate one-time navigation value may retain a validated path while the operation is active, but it never crosses the evidence persistence boundary.
6. The menu-bar/header/source composite is scanned again, then the review workspace permits additional irreversible manual masks.
7. Scopeproof encodes the reviewed PNG in memory, decodes and scans those exact bytes, and fails closed if the scan cannot complete or detects remaining sensitive content.
8. The same verified bytes are transactionally written and hashed under `~/Documents/Scopeproof Evidence`; a non-default identity uses `tenants/<tenant>/workspaces/<workspace>/` beneath that root. Before filesystem and Keychain state diverge, a tenant-bound Keychain commit journal records the intended image/manifest/lifecycle set and prospective capture-chain head. Startup either validates and commits the complete set or removes a partial set; conflicting/rollback state fails closed. The current manifest records the tenant/workspace, exact digest, local safety policy/time, and next signed local chain event. Discovery also reads the bounded legacy `~/Pictures/Scopeproof Evidence` root without an automatic move; new writes never target the legacy root. Unsigned/obsolete artifacts remain visibly unverified and browsing-only and must be recaptured for trust-bearing use.
9. Trust-bearing review decisions require macOS local-user authentication and are recorded in a separate signed, hash-chained lifecycle sidecar. The authenticated subject/method/time and a tenant/workspace/file-scoped Keychain rollback head are part of the verification contract. Lifecycle and legal-hold events use signing domains separate from capture provenance and from each other.
10. Optional upload returns a signed server receipt. Only Approved evidence is eligible for local assessor export.

Optional S3 storage follows the same saved artifact boundary. The Mac re-decodes the immutable manifest and confirms the screenshot digest, evidence ID, control ID, filename, tenant, and workspace before uploading the PNG and manifest to `<prefix>/tenants/<tenant>/workspaces/<workspace>/<control>/<assessment-period>/<evidence-id>/`. A local receipt binds the verified AWS identity, exact S3 versions/checksums, KMS/retention posture, tenant/workspace, and request IDs. S3 storage and Object Lock do not alter Scopeproof lifecycle state or make an artifact approved.

## Hosted evidence data flow

1. A scheduled/manual job calls a configured provider or receives an authenticated native upload. Every write resolves exactly one active assessment with an explicit, non-empty catalog/system/control scope; a client cannot widen that scope by naming a different framework, version, system, or control.
2. Textual evidence is scanned and redacted. Every screenshot follows one server-owned `lib/server/image-safety.ts` path: validate the PNG, submit the exact digest-bound pixels to the allowlisted scanner using the legacy `BROWSER_OCR_*` configuration, validate the response digest and policy, scan the returned text for sensitive values, discard that text, and retain only canonical safety-receipt metadata. Any scanner, content, digest, or policy failure stops the flow before storage.
3. A native upload must also pass schema-7 P-256 provenance verification, reserve the next exact per-device chain link, and obtain a trusted RFC 3161 attestation. Trusted time is mandatory by default and in production; if it is absent or verification fails, the upload returns an error before R2 storage. `REQUIRE_TRUSTED_TIMESTAMP=false` is diagnostic-only and causes production readiness to fail.
4. SHA-256 supports integrity checking and source/control de-duplication. A matching byte set reuses the encrypted artifact but creates an auditable collection-occurrence row; stable job/device retry identities make replays idempotent, while a genuinely new observation retains its receive time and provenance.
5. Evidence is encrypted with AES-256-GCM and stored in R2. D1 stores the IV, associated metadata, digest, review status, object key, occurrence count, last-observed time, and screenshot safety-receipt metadata; it does not store OCR text. Evidence validity is derived from the trusted receive time rather than a client-controlled timestamp.
6. For native evidence, the server finalizes the reserved device chain and immutable manifest-to-artifact link. Until finalization and a matching server safety receipt both exist, reads, approval, assessor packaging, and Jira attachment remain blocked. Older or unbound native rows therefore stay quarantined.
7. The material action or de-duplicated occurrence is appended to the HMAC-authenticated audit chain.
8. A different authorized reviewer loads the actual decrypted bytes, confirms the server-verified digest, and creates a durable review event. A collector/uploader cannot review the same occurrence. The event and optimistic state token commit together so only the concurrent-update winner is recorded.
9. Findings are durable assessment-scoped records with an append-only event trail. Reviewers may maintain ordinary finding state; compliance leads or administrators must perform risk acceptance or closure with a bounded disposition.
10. Package preflight computes eligibility from each artifact's latest occurrence across the complete assessment and blocks zero eligible evidence, unresolved scoped partial coverage, pending screenshot safety, pending native provenance, and over-limit selections. The builder repeats the global policy and every selected-occurrence condition in the final audited publication CAS, then decrypts approved evidence transiently, re-hashes it, indexes it, signs the canonical package manifest with ECDSA P-256, encrypts the package for R2, and exposes only an expiring download. Lost database responses are reconciled against the exact ready row; deletion requires a second authoritative failed/unreferenced proof.

## Repository SBOM data flows

### Hosted assessment evidence

1. A compliance lead or administrator selects an active assessment, repository source, ref, and output format. Managed mode uses a repository in `GITHUB_ORG`; one-time mode parses an exact GitHub URL and validates a short-lived token. Server-side authorization, same-origin checks, request-size validation, assessment/control scope, and a per-user hourly quota are enforced before a job is queued.
2. The Worker resolves the ref to a 40-character commit SHA through GitHub's API, then requests exactly one archive for that commit. It does not clone, check out, build, install, or execute repository content.
3. The Worker validates the ZIP directory before extraction and selects only recognized dependency lockfiles. Parsed components are normalized and de-duplicated by package URL with a hard component ceiling.
4. Scopeproof emits CycloneDX 1.6 or SPDX 2.3 JSON containing repository, commit, source-archive SHA-256, manifest, generator, and component provenance.
5. The result is stored through the ordinary encrypted evidence path and linked to an audited `sbom_jobs` record. A completed prior run for the same repository and assessment supplies a bounded added/removed/changed comparison. Repository identity and credential mode are retained; the credential is not.
6. An independent reviewer inspects and approves the linked evidence. Only approved, unexpired evidence is eligible for an assessor package.

One-time work has `max_attempts = 1`. If the request fails or its lease expires, the job fails closed and requires a new token; scheduled processing cannot reconstruct or reuse the credential.

### Native Mac direct export

1. An operator explicitly opens **Generate Repository SBOM…** and submits an exact GitHub HTTPS URL, a masked short-lived token, a ref, and a format. Input validation rejects other hosts, URL credentials, ports, query/fragment data, encoded path separators, unsafe refs, and malformed credentials.
2. A dedicated ephemeral URL session with no cache, cookies, credential store, or redirects calls only `api.github.com`. It resolves the ref to a 40-character commit, reads the bounded recursive Git tree, and requests only recognized lockfile blobs by validated Git object ID.
3. The Mac validates response, tree, manifest, UTF-8, aggregate-size, and component limits; parses the lockfiles in-process; and never invokes a subprocess, archive extractor, package manager, build tool, or repository source file.
4. The generator emits CycloneDX 1.6 or SPDX 2.3 with repository, immutable commit, manifest-set SHA-256, manifest paths, generator, collection method, and component provenance. The operator selects the destination; the app writes JSON and an adjacent checksum with mode `0600`.
5. The token field is cleared at submission and the token is released with the one request. No preferences, Keychain, local index, audit event, log, evidence record, cookie, cache, or retry queue contains it. The output remains a direct export and is not silently promoted into the hosted assessment lifecycle.

## Lifecycle and integrity model

- Current native capture manifests are immutable records of the final PNG, capture context, and tenant/workspace, signed with ECDSA P-256/SHA-256 and bound to a tenant-scoped monotonic capture chain. A Keychain commit journal reconciles the filesystem transaction with the capture head after interruption. Older/unbound native evidence is retained only as browsing/quarantined history until it is recaptured through the current path.
- Current local lifecycle records store only signed, hash-chained events with a separate tenant/workspace/file-scoped Keychain rollback head. Status, owner, authenticated reviewer subject/method/time, rationale, tags, supersession, and update time are projections of the final verified event; each event also binds the artifact digest and review/scanner policy versions. Local legal holds have an independent signing key and rollback head. Inconsistent or obsolete sidecars are never package eligible.
- Hosted assessments bind explicit systems and control IDs to an immutable versioned catalog digest. Review and finding state is evented and audited; hold release uses a digest-bound two-administrator request. Stable cursor pagination and server aggregates prevent page-size from changing compliance totals.
- Hosted audit events contain the previous event hash, a canonical event hash, and an HMAC. Database triggers block update/delete and reject a stale chain head. State mutations and their required audit insert share one D1 transactional batch, so either both commit or both roll back. Bounded verification trusts a checkpoint only when it was independently delivered, uses the configured ECDSA public key, and matches the live D1 sequence/hash/key/count before verifying the remaining tail.
- Package signatures authenticate the canonical manifest with an ECDSA P-256 signing key. The embedded public key enables verification; the fingerprint must be confirmed out of band.
- Hashes and signatures detect alteration. They do not replace source-system access controls, accurate scoping, reviewer judgment, or trusted endpoint security.

## Bounded operations

- Provider inventories, zones, branch-protection checks, URLs, retries, and due jobs are capped.
- Hosted repository SBOMs cap the compressed ZIP at 20 MB, archive entries at 5,000, selected manifests at 100 and 8 MB total, each manifest at 2 MB and 100:1 decompression, unique components at 5,000, generation at ten requests per user per hour, and due-job processing at three jobs per scheduler pass. Native generation caps the Git tree response at 8 MB/5,000 entries, selects at most 100 manifests at 2 MB each/8 MB total, emits at most 5,000 components, and permits one non-retrying run at a time.
- Native screenshot and manifest request sizes are capped and only PNG evidence with a valid schema-7 provenance signature, exact device-chain successor, trusted timestamp, and independent server safety receipt is accepted for hosted use.
- Hosted packages contain at most 100 approved artifacts and 25 MB of decrypted evidence and expire after seven days.
- Retry orchestration uses at most three attempts with bounded exponential backoff; authentication and unsafe-content failures do not retry automatically.
- The production native updater admits at most 10,000 ZIP entries, 1,024 UTF-8 path bytes per entry, 512 MiB actually expanded per file, 1 GiB actually expanded total, and a 200:1 per-entry and aggregate compression ratio. Before extraction it strictly reconciles central/local headers and data descriptors, streams stored/raw-deflate bytes to verify actual size and CRC-32, and rejects overlapping records, unsafe/ambiguous paths, and non-ordinary files. It repeats bounds after extraction and requires the verified expanded total plus 256 MiB reported free capacity. Release subprocesses permit 180 seconds and 1 MiB each of stdout and stderr; unknown capacity, cancellation, timeout, output overflow, or any validation failure terminates the operation and fails closed.

The D1 schema boundary for this architecture is `drizzle/0027_lonely_guardian.sql`. `npm run db:verify` must pass against fresh and populated fixtures before application deployment; it replays every migration in journal order and checks the native-chain, immutable-checkpoint, atomic checkpoint-retry, quarantine, independent-image-safety, explicit-scope, review-event, finding, and two-person hold-release invariants. See the [2026-09-01 remediation status](SECURITY_REMEDIATION_2026-09-01.md) for the source-versus-deployment boundary.
