# Scopeproof security model

> The conditional legacy hosted source is single-tenant. If separately authorized and deployed, it requires one exact canonical origin, one isolated D1/R2/key boundary, and `LEGACY_SINGLE_TENANT_ACKNOWLEDGEMENT=single-tenant-only`; this guard does not create multi-tenant isolation. The repository does not establish that a Sites deployment or its expected private identity dispatcher exists. The future AWS production boundary and its required tenant-isolation tests are documented in [AWS multi-tenant hosting](AWS_MULTI_TENANT_HOSTING.md); confirmed gaps and release blockers are tracked in the [AWS adversarial security review](AWS_SECURITY_REVIEW.md). Authentication or a Route 53 subdomain alone does not make the global legacy data paths safe for unrelated customers. The AWS source and templates in this repository have not been deployed. See [Security and product remediation status — 2026-09-01](SECURITY_REMEDIATION_2026-09-01.md) for the current source-control matrix and live-validation prerequisites.

Scopeproof handles security and compliance evidence that may expose sensitive configuration, identities, infrastructure, and control gaps. Deploy it as a high-sensitivity internal system and assume browsers, endpoints, provider responses, uploaded metadata, and assessors’ workstations may be compromised.

## Protected assets

- Evidence plaintext and decrypted assessor packages.
- Provider credentials and macOS device tokens.
- Evidence encryption, audit HMAC, and package-signing keys.
- User identity, roles, review decisions, Jira associations, and audit history.
- The integrity and availability of captures, manifests, receipts, and packages.
- Repository source provenance, generated SBOM contents, SBOM job history, and the GitHub read token used to access private source archives.

## Implemented controls

### Identity and authorization

- The legacy application consumes expected platform identity headers only on the single exact HTTPS origin in `TRUSTED_APP_ORIGINS` and only after the explicit single-tenant acknowledgement. It does not cryptographically authenticate those headers. Direct Worker, preview, alternate-domain, and misrouted requests must fail before identity is consumed, and an identity-aware private dispatcher must overwrite every client-supplied header variant before supplying authenticated values. Dispatcher support, header replacement, and exclusive ingress are external production gates that must be proven in the authorized deployed environment.
- Server-side permissions separate review from collection: reviewers inspect/approve, compliance leads collect/enroll/disclose, and administrators manage roles. An identity can never approve evidence it created or uploaded.
- Active assessments require one digest-verified versioned catalog plus explicit non-empty system and control scope. Evidence, collector, and SBOM paths repeat that binding server-side. The built-in PCI DSS operations catalog is intentionally limited and is not the complete standard.
- Evidence decisions are durable review events protected by optimistic concurrency. Findings are durable assessment-scoped records with an event trail: reviewers may maintain ordinary state, but only compliance leads or administrators can accept or close a finding with a rationale. A closed finding is terminal.
- Hosted hold release uses a 24-hour digest over the exact hold owner, reason, and expiry and requires approval by an administrator different from the requester. Replacing the hold cancels stale pending approvals.
- Initial administration requires a non-empty explicit email allowlist. A D1 invariant and atomic batch permit one bootstrap claim, bind its audit event, and preserve the final active administrator at the database layer. Every later user needs an audited, expiring invitation. Suspended or revoked owners cannot authenticate a Mac device, and collector/SBOM retries re-check the requesting member’s current permission before provider access.
- Mutation endpoints require an exact same-origin `Origin` and reject conflicting Fetch Metadata.
- Reviewers receive the actual decrypted, digest-verified artifact rather than a generated placeholder. Approval requires a matching full digest, a review rationale, and explicit scope/freshness/redaction confirmation.
- macOS devices use revocable random bearer tokens; only SHA-256 token hashes are stored server-side and the Mac stores its token in Keychain. Tokens expire after 30 days, rotation invalidates the prior token immediately, and owner suspension/revocation also blocks the device.
- Local mode requires no web identity or device token. The embedded console binds only to `127.0.0.1`. Its launch URL carries a one-time 256-bit nonce in the fragment; the bootstrap page exchanges it once for a different in-memory bearer, clears the fragment, and creates no localhost authentication cookie. Protected requests require the bearer and reject cross-origin, transfer-encoded, ambiguous, or browser-path-selected requests. Each server instance is bound to the tenant/workspace that created it; switching stops the previous console, invalidates its session, and rejects a suspended old request before it can return evidence.
- Native hosted tokens, evidence roots/manifests, S3 configuration/credentials/prefixes, capture-chain anchors, lifecycle anchors, and local legal-hold anchors are bound to one normalized tenant/workspace identity. A switch cancels S3 setup/retry/browser operations, closes and clears the S3 browser, removes Scopeproof's S3 credential and verified-destination Keychain items, invalidates the in-memory AWS session, and resets S3 preferences for the new identity. Trust-bearing lifecycle and hold actions also require macOS local-user authentication and record the authenticated subject, method, and time.
- Native source URLs are operator-confirmed or supplied by **Open URL & Capture**. Only HTTP(S) URLs are accepted. The evidence boundary persists and renders only the lowercase origin; user information, path, query, and fragment are removed in full because any of them can contain opaque bearer or tenant data. The origin is safety-scanned as part of the final screenshot, and hosted ingestion requires `sourceHost` to match its hostname.
- Jira Cloud uses OAuth 2.0 authorization-code flow. Rotating access and refresh tokens are AES-256-GCM encrypted with a dedicated hosted key and bound to a Scopeproof user and connection identity.

### Data protection and integrity

- Textual evidence is scanned for Luhn-valid PAN and supported secret/token families before persistence.
- Native screenshots never write the unreviewed source pixels to disk. Local OCR/redaction runs before and after stamping, the reviewed PNG is encoded in memory and scanned again, and the manifest binds the exact saved digest, scanner policy, and completion time. Hosted upload requires schema 8: the device signs the canonical manifest—including its tenant/workspace—with ECDSA P-256/SHA-256 and separately HMAC-authenticates the exact manifest/PNG digest pair with its bearer token. The server requires the signed tenant/workspace to match the isolated deployment, verifies both cryptographic bindings, strictly parses/decompresses the bounded PNG, validates the capture session, and reserves then finalizes the next exact sequence/hash on one monotonic per-device chain. Local scan results remain client claims and are never sufficient by themselves for hosted trust.
- Every hosted screenshot, including native uploads and Cloudflare Browser Rendering captures, passes through the same independent server safety boundary in `lib/server/image-safety.ts` before storage. The legacy-named `BROWSER_OCR_ENDPOINT`, `BROWSER_OCR_TOKEN`, and `BROWSER_OCR_ALLOWED_HOSTS` settings select one clean HTTPS endpoint on an exact hostname allowlist. Its bounded response may contain only the submitted SHA-256, recognized text, and a policy version; Scopeproof scans the text transiently, rejects sensitive findings, and persists only the image digest, policy, completion time, scanner origin, and canonical receipt hash. Scanner unavailability, extra/malformed response fields, digest mismatch, invalid policy, or sensitive content fails closed.
- Native evidence is disclosed, approved, added to a hosted assessor package, or attached to Jira only when its immutable native-manifest link matches the artifact and the enrolled device's finalized chain/key state, and its independent server safety receipt matches the exact artifact digest. Older-schema, unbound, and interrupted pre-finalization records are quarantined from those operations rather than silently grandfathered.
- The scheduled legacy reconciler uses independent durable circular keysets and budgets: at most 25 expired native reservations and, separately, at most 25 due entries from the sparse native-artifact reconciliation queue per invocation. It finalizes only the exact next device sequence when the pinned key, chain tuple, artifact owner/source/digests, scanner receipt fields, timestamp, device, and membership remain valid. The final mutation and its audited postcondition recheck that the same owner is currently active and still has an `admin` or `compliance_lead` role, exactly matching `collect_evidence`; suspension or demotion loses the CAS. Otherwise it conditionally releases the expired reservation, moves an eligible due orphan to audited `returned` state with approval cleared, or drains a finalized, missing, or otherwise terminal queue entry. An artifact remains ineligible for the orphan transition while its device has any pending reservation, even an expired one, preserving exact-finalization retry after a transient database, audit, or key-validation failure. It never infers a predecessor, reads/deletes R2 bytes, or advances a mismatched chain.
- The AWS shared maintenance worker does not expire an issued upload at its client upload deadline. It validates a fifteen-day post-reconciliation TTL buffer and preserves the intent through the full seven-day delayed GuardDuty/event reconciliation window used by promotion; only the exact status, revision, expiry, TTL, and dual-index authority can transition after that deadline. A protected tenant directory and base-PK V2 sparse index prevent cross-tenant maintenance partition forgery, independent per-tenant lifecycle/action budgets prevent one tenant from starving the others, deterministic poison rows are drained without logging raw keys, and provider failures remain retryable through SQS. Stale or malformed work creates a durable digest-only action ledger with repeated count/age alarms until exact promotion, recovery, or rejection resolves it transactionally. Legacy GSI1 remains dual-written for the staged rollback window; the worker cannot update before V2 creation/backfill completes.
- Evidence and generated packages are encrypted with AES-256-GCM in R2.
- D1 contains metadata, object references, IVs, and integrity digests rather than evidence plaintext.
- Audit events are canonicalized, hash-chained, HMAC-authenticated, and protected from update/delete by D1 triggers. Security-sensitive D1 mutations and their audit event execute in one transactional batch; a stale audit head rolls the entire batch back and retries. Bounded verification begins at the newest independently delivered signed checkpoint, requires the configured package public key, and cross-checks the real D1 event hash/key/count before trusting the tail. Before a witness call, one worker atomically claims a two-minute delivery lease; failures append a bounded code, back off from one minute to six hours, recover stale claims, and enter `action_required` after ten unsuccessful claims. The exact same-head envelope uses a digest idempotency key; a successful signed receipt is append-only and immediately invalidates a cached failure. Repeated audit failures emit metadata-only error classes, never exception text.
- Artifact-byte de-duplication does not erase collection freshness. Every accepted collection records an immutable occurrence with capture/receive times and bounded job, device, session, assessment, scanner, and chain provenance. Stable retry identities make replays idempotent while distinct collections remain visible.
- Package creation runs a fail-closed preflight over the full assessment and refuses zero eligible evidence, unresolved partial coverage, missing independent screenshot safety, pending native provenance, or a selection that would exceed the 100-artifact non-truncation limit. Preflight and build call one latest-occurrence, behavior-tested eligibility policy. The final audited publication CAS rechecks every selected occurrence and the global blocker/count fence; ambiguous commits are authoritatively read back, and an R2 candidate is deleted only after a second database read proves it is an unreferenced failed loser.
- The local SQLite index is non-authoritative and rebuildable from manifests. Its audit table is hash-chained, authenticated with a device-only Keychain key, verified before every append, and protected from update/delete by SQLite triggers. New local evidence is written under `~/Documents/Scopeproof Evidence`; a non-default identity uses `tenants/<tenant>/workspaces/<workspace>/` beneath that root. Files use macOS complete file protection and account-only permissions; legacy Pictures-based evidence remains readable. A tenant-bound Keychain capture journal reconciles complete filesystem commits with the monotonic capture head after interruption. Managed endpoints should enforce FileVault and prevent unapproved iCloud Drive, backup, or enterprise synchronization of the evidence folders.
- Current local lifecycle and legal-hold events are independently signed, authenticated to the macOS user, and protected by separate monotonic Keychain heads. Legal-hold scope uses immutable tenant, workspace, evidence ID, and artifact digest values rather than a mutable path. A missing marker with either a committed or pending head is invalid and blocks retention; valid legacy markers are adopted into the immutable scope before use. A two-phase pending advance permits safe recovery when a sidecar write succeeds but the anchor update is interrupted.
- Assessor manifests are ECDSA P-256/SHA-256 signed and include independent artifact hashes.
- Jira URLs require HTTPS, issue keys are format-restricted, and native Jira metadata must match the immutable manifest.
- Jira API calls use fixed Atlassian hosts and server-selected cloud IDs. OAuth state is random, user-bound, stored only as a hash, single-use, and expires after ten minutes. Requested sites must end in `.atlassian.net`, match Atlassian’s accessible resources, and use configured project allowlists.
- Jira uploads require explicit confirmation and revalidate the device, finalized monotonic provenance link, independent server safety receipt, issue, project, PNG digest, Approved lifecycle chain, and attachment limits. A durable idempotency reservation prevents concurrent duplicate attachment sets; ambiguous network/provider outcomes require reconciliation instead of automatic replay. OAuth refresh-token rotation is serialized with an expiring lease and optimistic token version. Signed upload receipts and audit events exclude token material.
- Repository SBOM creation is restricted to compliance leads and administrators, while evidence approval remains independent. Managed mode constructs the repository owner from fixed `GITHUB_ORG`; one-time mode accepts only an exact HTTPS `github.com/owner/repository` URL. Both validate repository/ref syntax, require an active assessment with PCI DSS 6.3.2 and matching system scope, and resolve the requested ref to an immutable commit before inventory generation.
- GitHub access is read-only and destination-restricted to `api.github.com` and the exact `codeload.github.com` archive redirect. Managed credentials remain server-side. A one-time token is masked, cleared from the form at submission, held only for the request, and excluded from D1, R2, jobs, evidence, audit details, logs, settings, browser storage, and Keychain. One-time jobs have one attempt and fail closed rather than retrying without a credential. Generated JSON uses the same evidence encryption, digest, lifecycle, download-audit, retention, and package controls as other hosted evidence.
- Native one-time SBOM export connects only to `api.github.com` through an ephemeral session with redirects, cookies, URL cache, and credential storage disabled. It resolves a commit and downloads only selected lockfile blobs, never archives or source code. The masked token is cleared at submission and excluded from preferences, Keychain, local evidence, indexes, audit events, logs, cookies, caches, and retry state. The direct JSON/checksum output is mode `0600` but remains operator-managed and does not inherit hosted encryption, RBAC, lifecycle, approval, retention, or package controls.
- Native S3 production mode requires expiring STS credentials, a nonempty prefix, customer-managed SSE-KMS/DSSE-KMS, Block Public Access, versioning, BucketOwnerEnforced ownership, COMPLIANCE Object Lock retention, an enabled S3 Bucket Key for SSE-KMS, and the exact bucket policy denying non-TLS access, bucket/evidence deletion, Governance bypass, and incorrect encryption/key writes. Governance is non-production because privileged identities can bypass it. Before enabling uploads, the app binds the KMS ARN to the STS-verified bucket-owner account, partition, Region, tenant, and workspace; calls `kms:DescribeKey` on that exact ARN; and requires `CUSTOMER`, `ENCRYPT_DECRYPT`, `SYMMETRIC_DEFAULT`, and `Enabled` metadata with no pending deletion. Only manually entered credentials use a `WhenUnlockedThisDeviceOnly` Keychain item; Identity Center and one-hop AssumeRole credentials stay in memory. The verified caller-account/destination/bucket/KMS posture binding uses its own device-only Keychain item, and preference or tenant/workspace tampering invalidates it. Object operations are restricted to `<prefix>/tenants/<tenant>/workspaces/<workspace>/`. Requests use generated S3/STS/KMS or FIPS hosts, TLS 1.2+, SigV4, expected-owner headers, an ephemeral cacheless/cookieless session, and redirect rejection. PUTs require returned SHA-256, version ID, encryption, and KMS-key agreement. Browsing lists at most 5,000 immutable versions; the Local Console exposes only normalized metadata and evidence IDs, never object keys or credentials. It does not infer identity from a key: `Local + S3` requires a local receipt matching the destination, tenant/workspace, exact image/manifest keys, versions, ETags, S3 checksums, and local digests. S3-only pairs are lifecycle-invalid and provenance-unverified. An on-demand preview fetches the paired exact-version manifest first, then validates the PNG SHA-256, enforces 40 MiB, uses a mode-`0700` temporary directory, and deletes it after the authenticated loopback response. Native downloads additionally receive private permissions and macOS quarantine metadata. Receipts contain exact versions and request IDs but no credential. Local expiry cleanup never trusts the receipt alone: it performs live exact-version `HEAD` and Object Lock retention checks and blocks cleanup unless every receipt object still matches its version, ETag, checksum, KMS posture, and future COMPLIANCE retention.
- The AWS source requires production tenants to configure an exact-version HTTPS DLP scanner, KMS-encrypted scanner-token secret, and policy version. Promotion accepts only a strict `CLEAN` result for the immutable quarantine version; canonical DLP and promotion facts are KMS-signed and reconciled against destination S3 metadata, DynamoDB, and PostgreSQL. Rejected evidence uses an immutable canonical receipt: an exact DynamoDB-first replay is idempotent before freshness enforcement, while a missing Aurora receipt can recover only within the 14-day ingest DLQ horizon and must still match tenant, intent, evidence, version, revisions, digest, and stored rejection time. API Gateway OAuth scopes are additive to Lambda JWT, host, membership, role, database, IAM, and KMS controls. These controls have not been validated in a live AWS deployment.

### Abuse resistance

- Provider requests, opaque database cursors, browser targets, retries, due work, upload sizes, package counts, and decrypted package bytes are bounded. Assessment/evidence/run/SBOM/finding/package summaries are computed across the filtered database set rather than inferred from the current page. Link-based provider pagination stays on the original clean HTTPS origin, so bearer credentials cannot follow an attacker-controlled cross-origin `next` URL. Provider response bodies are never copied into stored/operator errors.
- Browser collection permits HTTPS targets only. Its screenshot uses the same independent scanner as native hosted uploads, verifies the exact clean HTTPS origin, response schema, PNG digest, and policy version, and fails closed before storage on service errors, malformed/mismatched results, or sensitive recognized pixels.
- Repository archives are untrusted in the hosted workflow. Scopeproof validates the central directory before extraction, rejects malformed/oversized/over-compressed archives and non-UTF-8 or NUL-containing manifests, extracts only recognized lockfiles, caps parsed components, and never invokes source files, package managers, install hooks, build tools, containers, or subprocesses. Native generation avoids archives entirely and applies equivalent tree/blob/manifest/component bounds.
- SBOM generation permits ten requests per authenticated user per hour, uses leased jobs with bounded retries only for transient provider failures, and caps scheduler work to prevent one repository from monopolizing execution.
- Error responses use request IDs and avoid returning server exception details to clients.

## Secure operating requirements

1. Use a private Sites access policy and grant the minimum role required.
2. Configure `BOOTSTRAP_ADMIN_EMAILS`, one exact canonical `TRUSTED_APP_ORIGINS`, `LEGACY_SINGLE_TENANT_ACKNOWLEDGEMENT=single-tenant-only`, and exact lowercase `LEGACY_TENANT_ID`/`LEGACY_WORKSPACE_ID` values before hosted use. The application has no cryptographically verifiable dispatcher assertion; prove the external identity-header overwrite/exclusive-ingress gate separately. Missing or unsafe tenant/workspace values make current native ingestion unavailable by design. After bootstrap, create users only through **Settings → Team & access**.
3. Apply D1 migrations in journal order through `drizzle/0028_native_reconciliation_cursor.sql`, then run `npm run db:verify` before deploying the corresponding application build. Do not skip either the fresh-database or populated upgrade-path replay.
4. Use distinct, high-entropy encryption, audit, and signing keys. Store them only in the hosted secret manager.
5. Configure the required security-monitoring endpoint and exact host allowlist; any optional bearer token must be trimmed, 16–4096 characters, and control-free. Configure the independent screenshot scanner with all three legacy-named `BROWSER_OCR_*` settings and the exact clean HTTPS host contract. Configure the approved RFC 3161 TSA/verifier, pinned verifier key, allowlist, token, and trust anchor; keep `REQUIRE_TRUSTED_TIMESTAMP=true` for every production environment.
6. Use least-privilege, read-only provider credentials and dedicated accounts where supported. The legacy AWS collector requires a complete temporary STS access-key/secret/session-token set and rejects long-lived two-part credentials.
7. Restrict browser capture URLs to an explicit approved list and avoid pages containing cardholder or customer data.
8. Require managed, encrypted macOS endpoints with screen lock, malware protection, and current OS updates.
9. Verify Jira project permissions, automation rules, marketplace apps, backups, and retention before attachment.
10. Review audit-chain health, device inventory, collector errors, failed jobs, expiring evidence, and package downloads routinely.
11. Rotate or revoke a device/provider credential immediately after suspected exposure.
12. Preserve old encryption-key material under controlled key-version procedures until all dependent evidence is expired or re-encrypted.
13. Restrict `GITHUB_TOKEN` to the intended repositories with Metadata and Contents read access only. Rotate it, monitor GitHub access, remove repositories no longer in scope, and leave SBOM generation unconfigured rather than granting broad organization access.
14. For one-time SBOM access, use a dedicated short-expiry repository-scoped token, prevent password-manager saving where applicable, revoke it after use, and treat the operator browser or Mac endpoint as part of the credential trust boundary.
15. For S3 storage, use IAM Identity Center or AssumeRole temporary credentials. Separate setup/verifier, upload-only, and optional browser roles; never grant the daily role bucket administration or deletion. Production setup additionally needs the documented ownership, KMS, Object Lock, policy, and optional lifecycle/replication actions, then those permissions must be removed. A temporary Compatible S3 exception must use a dedicated no-console IAM user, an exact bucket/prefix identity policy, and a KMS key-policy principal constrained by caller account, regional S3 service, and encryption context; never use a personal or administrator key. Deploy the prefix-scoped CloudTrail/SNS template, confirm alert delivery, and test exact-version recovery.

## Residual risks and limitations

- OCR and pattern matching cannot guarantee detection of every sensitive value. Native operator preview remains mandatory, and the independent scanner requires a separate security/privacy review because both native and Browser Rendering screenshot pixels are disclosed to that processor. Scopeproof intentionally does not retain the scanner's recognized text.
- A compromised endpoint can display falsified source content or capture manipulated pixels.
- Local timestamps depend on the Mac clock. Production hosted native ingestion therefore requires a third-party timestamp before storage. It is accepted only after a pinned verifier attests the RFC 3161 success status, SHA-256 message imprint, request nonce, CMS signature, TSA `timeStamping` EKU, certificate path, configured trust anchor, validity window, and revocation status. Absence or failure rejects the upload before R2 persistence. `REQUIRE_TRUSTED_TIMESTAMP=false` is for diagnostics only: it permits a receipt containing Scopeproof signed server time and a bounded error, but the production-readiness check remains failed and such a configuration is not production-authorized.
- Live menu-bar pixels provide useful assessor context but remain endpoint-controlled evidence: the clock can be changed, status items can expose sensitive information, and a compromised Mac can display deceptive content. Scopeproof scans and presents the strip for redaction, but independent time assurance still requires the signed server receipt or a verified RFC 3161 attestation.
- Operator-imported control catalogs are bounded, normalized, checked for duplicate identifiers, and recorded with their SHA-256 digest. Those controls remain operator-authorized input rather than publisher-authenticated content; verify catalog version and provenance against the framework publisher or an approved GRC source before use. Existing evidence retains its original catalog metadata when selections are updated.
- Current local lifecycle records derive all projected state from the final signed, anchored event. Every event binds authenticated macOS subject/method/time, artifact digest, review policy, scanner policy, owner, rationale, tags, and supersession state. Separate lifecycle and legal-hold keys/anchors reduce cross-domain substitution. Obsolete/unbound or inconsistent sidecars are draft/ineligible and require recapture. The package-signing identity remains a separate user-presence-protected Keychain item.
- The package’s embedded public key must be fingerprint-verified out of band to establish signer continuity.
- Jira permissions, issue security, marketplace apps, notifications, backups, exports, retention, and downstream sharing remain outside Scopeproof’s control. Timeout failures can leave an ambiguous attachment outcome that must be inspected before retry.
- Spreadsheet CSV indexes are presentation-only and prefix formula-like cells (including after leading ASCII whitespace/control characters) with an apostrophe. Use the signed JSON manifest for machine verification.
- Update trust depends on protecting the offline release private key and accurately provisioning its matching public key and validity window in the signed app bundle. An empty key list fails closed and intentionally disables updates.
- Provider coverage is intentionally bounded and may require additional collection for large environments.
- Repository SBOM coverage is limited to supported pinned lockfiles and the first 250 repositories returned for the configured organization. Static parsing cannot prove the deployed artifact, dynamically loaded dependencies, vendored code, generated lockfiles absent from the commit, transitive resolution performed outside a supported lockfile, vulnerability status, or license obligations.
- A compromised GitHub organization administrator or source repository can supply deceptive lockfiles. Commit immutability and archive hashing establish what Scopeproof parsed, not that the source is trustworthy; require protected branches, change review, release provenance, and vulnerability analysis as separate controls.
- One-time input avoids long-term application storage but cannot guarantee zeroization of every transient process-memory copy or protect a token from a compromised browser, extension, Mac endpoint, crash collector outside Scopeproof, organization-managed TLS inspection, or GitHub access logging. Use managed endpoints and narrowly scoped, short-lived credentials; do not use a personal broad-scope token.
- S3 availability, IAM/Identity Center administration, destination replication policy, legal holds, KMS recovery, retention approval, CloudTrail cost/retention, and downstream readers remain AWS/customer responsibilities. The app can start AWS CLI v2's IAM Identity Center browser login from a reviewed fixed executable path and then keeps the resulting short-lived credentials only in memory; manual STS entry remains the break-glass path. A compromised unlocked Mac can use a live session within its IAM permissions, so keep it prefix-scoped and short-lived. Deep Archive restore time/cost and deletion lifecycle remain explicit customer decisions.
- Key rotation is not automatic; replacing an encryption key without a migration can make prior evidence undecryptable.
- An ad-hoc local macOS build is not notarized and does not provide a Developer ID trust chain.
- The development-preview DMG checksum detects accidental or malicious byte changes only when obtained from a separately trusted release page. It does not authenticate the publisher, replace Developer ID signing/notarization, or make the preview appropriate for managed production deployment.

## Incident response

If evidence, a token, or a signing/encryption key may be compromised:

1. Stop affected collectors or Jira transfers and preserve relevant logs and hashes.
2. Revoke affected macOS device tokens and provider credentials.
3. Restrict site and Jira access; identify downloads, exports, and downstream recipients.
4. Rotate exposed keys using a documented migration and recovery plan. Do not destroy keys still required to decrypt retained evidence.
5. Verify the hosted audit chain and compare affected artifact/package hashes.
6. Recapture or rebuild evidence when provenance or confidentiality cannot be established.
7. Record containment, impact, decisions, notifications, and recovery evidence in the incident system.

Report vulnerabilities privately through the GitHub repository’s Security Advisory feature. Do not include real credentials, PAN, customer data, or production evidence in a public issue.
