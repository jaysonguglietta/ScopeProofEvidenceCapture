# Production operations, recovery, and incident response

This runbook is the minimum operational control set for using the current Scopeproof service as a compliance-evidence system of record. Assign named owners and store completed records in an organization-controlled change/incident system. The current application remains single-tenant: deploy a separate Sites project, D1 database, R2 bucket, identity policy, and key set for every legal entity or isolation boundary. The selected [AWS multi-tenant replacement](AWS_MULTI_TENANT_HOSTING.md) has its own [AWS platform runbook](AWS_PLATFORM_RUNBOOK.md) and [adversarial security review](AWS_SECURITY_REVIEW.md); it may serve additional customers only after its staged migration and Client A/Client B isolation gates pass. No AWS environment has been deployed by the repository work described here; the AWS stacks and CloudFormation files are templates until an authorized operator deploys and validates them.

## Service objectives

Approve organization-specific objectives before launch. The recommended starting targets are a 24-hour recovery point objective for D1 metadata and R2 ciphertext, a 4-hour recovery time objective for read-only evidence access, and an 8-hour objective for resumed collection. Reduce the RPO when an active assessment cannot tolerate recreating one business day of evidence.

## Native hosted-ingestion production gate

Local-only capture is a separate availability boundary. A Mac may continue local capture, redaction, review, search, retention, and package export without a hosted scanner or timestamp service. Do not describe that local result as hosted-trusted evidence until the server pipeline below completes.

Before accepting native evidence in production:

1. Apply and verify every database migration through `0028_native_reconciliation_cursor.sql`. In particular, `0020_native_device_chain.sql` adds the device-chain state, `0022_native_provenance_quarantine.sql` adds immutable native provenance/finalization fields, `0023_independent_image_safety.sql` adds the exact-pixel server-scan binding, `0025_pink_malice.sql` adds immutable independent-checkpoint delivery attempts, `0026_omniscient_scarlet_witch.sql` adds durable per-record key-rotation retry state, `0027_lonely_guardian.sql` adds atomic checkpoint-delivery claims, bounded backoff, stale-lease recovery, and terminal action-required state, and `0028_native_reconciliation_cursor.sql` adds the bounded sparse native-reconciliation queue and independent durable cursor state.
2. Configure `BROWSER_OCR_ENDPOINT`, `BROWSER_OCR_TOKEN`, and `BROWSER_OCR_ALLOWED_HOSTS` for an independently operated OCR/DLP processor. These names are retained for compatibility but govern all hosted screenshot ingestion, including native uploads. The endpoint must return the digest of the exact submitted PNG and an approved policy version. Recognized text is evaluated transiently and must not be stored, audited, logged, or sent to monitoring; persist only the digest-bound policy, scanner origin, completion time, and receipt digest.
3. Set `REQUIRE_TRUSTED_TIMESTAMP=true` and configure the RFC 3161 issuer and verifier values, verifier host allowlist/public keys, and TSA trust-anchor fingerprint. A Scopeproof server clock signature alone is not the production timestamp control.
4. Confirm `GET /api/admin/readiness` reports no failures. Readiness structurally parses the single trusted-origin configuration and bootstrap administrator allowlist; it also requires the security-monitoring endpoint/allowlist and the independent scanner's one clean HTTPS endpoint, exact hostname allowlist, and trimmed 16–4096-character control-free token. The `security_monitoring`, `independent_image_safety`, trusted-origin/bootstrap, trusted-timestamp-policy, and trusted-timestamp checks must pass. Missing or merely present-but-malformed settings, an unsafe endpoint/allowlist/token, disabled timestamp enforcement, or incomplete timestamp trust material makes the service not production-ready.
5. Exercise one current schema-8 upload end to end. Verify the server checks the signed tenant/workspace against `LEGACY_TENANT_ID`/`LEGACY_WORKSPACE_ID`, device P-256 signature, and exact digests; independently scans the exact PNG; verifies the RFC 3161 result; reserves the next contiguous device sequence; stores the artifact; and finalizes the artifact/digest/event/key linkage.

The read, preview, approval, package/export, and Jira disclosure paths must continue to fail closed when the independent scan binding or final native-chain link is missing. Scanner or required-timestamp failure before storage should return a recoverable error and store nothing. A cross-store failure after storage is a quarantine condition: preserve the record, block disclosure, and retry the original exact schema-8 upload to reconcile it. Older evidence that lacks the signed tenant/workspace must be recaptured for hosted use; never backfill trust fields, change status directly, or grandfather a population with a blanket SQL update.

Audit checkpoints and their delivery history are also append-only. A new checkpoint first commits its signed envelope and immutable D1 row. If independent delivery is missing or failed, the scheduler may retry that exact envelope only while its sequence, event hash, and HMAC key remain the current audit head. Before network access, one worker atomically claims the due retry with a two-minute lease; other workers must stand down. Failed claims use exponential backoff from one minute to six hours, stale claims are recoverable, and the tenth unsuccessful claim transitions to `action_required`. Every witness POST carries an `Idempotency-Key` equal to the checkpoint SHA-256; the witness must replay the same signed receipt for that key so a timeout or crash after acceptance cannot create a second external assertion. Each claimed endpoint attempt appends either a bounded failure code or one signed delivered record; a partial unique index permits only one delivered attempt per checkpoint. Successful receipt envelopes use unique R2 keys and bind the delivery-attempt ID, checkpoint ID/digest/sequence, endpoint origin, timestamps, external signed receipt, and Scopeproof signature. Concurrent or ambiguous outcomes preserve the candidate until authoritative database state proves it is unreferenced; a proven loser may then delete its object and adopt the immutable winner. Verification re-reads the exact R2 body and metadata, verifies both signatures and every binding, and fails closed on any mismatch. Never update `audit_checkpoints`, `audit_checkpoint_delivery_attempts`, or `audit_checkpoint_delivery_retry_state` manually. Repair a retryable failure and let the same-head retry proceed. After terminal `action_required`, repair the witness path and append an audited operational event so a new audit head can create a new checkpoint.

## Backup control

At least daily, capture or verify:

1. A restorable D1 snapshot/export that includes its capture time and platform restore identifier.
2. An inventory of every R2 object key, size, ETag/digest metadata, and capture time. Replicate ciphertext to an organization-controlled account or storage service with retention/immutability enabled when policy requires account-level disaster recovery.
3. Every retained encryption/HMAC key version, the package-signing recovery key, public-key fingerprints, Jira client configuration, Sites configuration, and release public metadata. Key escrow must be encrypted under a separately controlled recovery key with dual-person access.
4. The deployed Git commit, Sites version identifier, migrations applied, macOS release envelope, notarization log, release SBOM, and representative repository-SBOM job/evidence metadata. Keep release and repository SBOMs labeled separately.
5. A JSON backup manifest listing each exported file as `{ "path": "relative/path", "sha256": "..." }`. Verify it with `node Scripts/verify_backup_manifest.mjs backup-manifest.json` before marking the backup successful.

Never place plaintext evidence or production secrets in an ordinary workstation backup. Keep backup access separate from application-administrator access and alert on backup deletion, retention changes, restore activity, and failed daily verification.

## Quarterly recovery drill

1. Create an isolated recovery Sites project and new restricted operator identities.
2. Restore D1 and R2 ciphertext from a selected recovery point without connecting collectors or Jira.
3. Restore all referenced keys. Run the administrator readiness endpoint; missing-key references are a failed drill.
4. Verify the full audit chain and the latest signed checkpoint against the independently retained public-key fingerprint and external checkpoint copy.
5. Download a stratified sample covering each retained encryption key, evidence type, assessment, and month. Verify plaintext SHA-256 values.
6. Generate and independently verify an assessor package. Do not send it to production Jira.
7. Record actual RPO/RTO, sample IDs/digests, deviations, owners, corrective issues, and destruction of the isolated recovery environment.

## Monitoring and alerting

Configure the required `SECURITY_EVENT_ENDPOINT`, exact `SECURITY_EVENT_ALLOWED_HOSTS` hostname allowlist, and separate `SECURITY_EVENT_TOKEN` for the organization monitoring ingress. The token must be trimmed, 16–4096 characters, and contain no control characters. Production readiness and delivery fail closed if any value is missing or unsafe. Every scheduler run sends an HMAC-authenticated, bearer-authenticated, metadata-only health record containing 24-hour failure counts and checkpoint health. Configure the receiver with the retained audit HMAC keys and alert on signature failure, missing health records for 30 minutes, collector action-needed state, failed jobs/packages/purges, unresolved Jira uploads, or stale/failed audit checkpoints.

Also alert from platform logs on `scopeproof_api_error`, `scopeproof_audited_batch_failure`, `scopeproof_audit_checkpoint_delivery_failure`, `scopeproof_audit_checkpoint_delivery_action_required`, `scopeproof_maintenance_stage_failure`, `scopeproof_key_rotation_action_required`, `scopeproof_key_rotation_failure_tracking_failed`, `scopeproof_key_rotation_recovery_tracking_failed`, `scopeproof_rekey_old_object_delete_failure`, and sustained rate limiting. Error telemetry uses allowlisted classes/codes; do not send exception messages, evidence contents, OAuth tokens, user tokens, OCR text, or secrets to monitoring.

Key-rotation failures are isolated per evidence, package, or Jira connection. Each failed record receives exponential backoff; after five attempts it remains safely retryable on a long interval but is marked `action_required` and must page an operator. Repair the missing object/metadata/key or storage/database fault without deleting historical keys, then allow the scheduler to complete the audited `key.rotation_recovered` transition. A poisoned record must not prevent later healthy records, audit checkpoints, or operational-health delivery from running.

Alert separately on independent screenshot scanner unavailability, digest mismatch, disallowed scanner origin, sensitive-content rejection, RFC 3161 issuance/verification failure, device-chain reservation conflict, and native finalization backlog. Alerts may contain bounded evidence/device identifiers and failure codes, but never PNG bytes or recognized OCR text.

For repository SBOM operations, review `sbom_jobs` for sustained `failed`, overdue `retrying`, or expired `running` leases; spikes in `GITHUB_AUTH_FAILED`, `REPOSITORY_OR_REF_NOT_FOUND`, `ARCHIVE_LIMIT_EXCEEDED`, `INVALID_ARCHIVE`, `INVALID_MANIFEST`, or `COMPONENT_LIMIT_EXCEEDED`; and repeated rate limiting. Authentication failures require token repair or rotation and are not automatic retries. Archive/manifest/component failures require repository-owner remediation or a reviewed limit/parser change—not a blanket limit increase. After credential rotation, generate a canary SBOM from a known repository and confirm a completed audit trail.

One-time jobs intentionally have one attempt. `LEASE_EXPIRED` or transient GitHub failures require a fresh operator submission because Scopeproof retains no credential. Do not add the token to a ticket or log to make a job replayable. Review infrastructure/request logging configuration to ensure JSON request bodies are excluded, and investigate any suspected browser, extension, endpoint, or proxy capture as a credential incident.

Repository SBOM evidence follows the ordinary evidence expiration, legal-hold, encryption-key, approval, download, and assessor-package controls. Retain job metadata and the source/archive/artifact digests for the approved retention period. Do not retain downloaded GitHub ZIPs; Scopeproof processes them transiently and persists only the generated encrypted SBOM plus provenance metadata.

Review `evidence_occurrences` alongside artifact counts. De-duplication intentionally stores one encrypted byte set but one occurrence per distinct collection, including receive time and job/device/session provenance. A collector that reports zero new artifacts may still have refreshed existing evidence; confirm its occurrence count and last-observed time. Stable retry occurrences must not multiply after a replay. Investigate occurrences created by revoked identities, impossible future capture times, or jobs outside the active assessment.

Native Mac SBOM exports are deliberately outside hosted retention and approval controls. Require operators to retain the JSON and adjacent checksum in an approved encrypted evidence location, record the immutable commit and reviewer decision, transfer them through an approved channel, and dispose of them under the applicable schedule. The one-time token must be revoked after the run and must never be copied into a ticket, command history, evidence file, or troubleshooting log.

For native S3 evidence storage, deploy `infra/aws/scopeproof-s3-observability.yaml` into the evidence account, confirm the SNS subscription, and retain CloudTrail logs in the separately named Object-Locked log bucket. Alert on evidence deletion, posture changes, and KMS disable/deletion/policy changes. Exercise a controlled alert and exact-version recovery before launch and at least annually. Treat checksum, expected-owner, destination-binding, version-ID, or posture-verification failures as integrity events; disable automatic upload until they are resolved.

Inventory the AWS principal used by every Mac. Production principals must be expiring STS sessions. Any Compatible S3 IAM-user exception must have a named owner and removal date, no console access or unrelated policies, exact bucket/prefix and KMS-context restrictions, key rotation monitoring, and an approved migration plan to temporary credentials.

Review hosted invitations, memberships, and capture devices at least monthly and on every personnel/role change. Expire or revoke unused invitations, keep two active administrators, suspend access immediately during investigation, and revoke rather than merely deleting a local token. Rotate device tokens before their 30-day expiry and confirm the Mac reconnects with the replacement. Queued collector and SBOM retries must fail with `AUTHORIZATION_REVOKED` after their requester loses permission; alert if provider calls continue.

## Incident response

Severity 1 includes suspected key compromise, audit-chain/checkpoint failure, unauthorized evidence access, cross-boundary exposure, malicious release/update, or loss of both primary and recovery data. Immediately stop collection/export/Jira transfer, preserve logs and external checkpoints, revoke affected device/OAuth/provider credentials, restrict administrator access, and open the security incident process. Do not rotate away or destroy a suspected key before preserving a controlled recovery copy needed to analyze historical records.

For integrity incidents, compare the database head with independent checkpoints, restore into isolation, identify the earliest divergence, and treat later assertions as untrusted until re-established. For confidentiality incidents, identify affected assessment/evidence IDs from metadata, determine whether ciphertext and keys were both exposed, follow contractual/regulatory notification procedures, and reissue provider/Jira credentials. For release compromise, remove hosted release metadata, revoke/notarization credentials where supported, publish an independently communicated block notice, and ship a higher monotonic sequence signed by a new trusted update key.

Close an incident only after root cause, evidence preservation, containment, eradication, recovery validation, notification decisions, key/credential rotation, control improvements, and an owner/due date for every follow-up are recorded.

## Launch authorization checklist

- Named application, security, backup, Jira, and assessment owners are assigned.
- DPA/privacy review, data classification, retention schedule, legal-hold process, and data-residency decision are approved.
- Production secrets are organization-owned; readiness has no failures; external audit checkpoint and monitoring delivery are tested.
- Migrations are applied through `0028_native_reconciliation_cursor.sql`; the sparse native-reconciliation queue and independent pending/orphan cursor state are healthy; independent screenshot scanning is configured through the legacy-named `BROWSER_OCR_*` settings; recognized OCR text is not retained; and the required RFC 3161 trust boundary is configured and tested. Production readiness fails when either service is disabled, missing, unsafe, or unverifiable. The private Sites identity-header boundary and exclusive ingress are separately proven with deployed negative tests.
- At least two named administrators and separate collector/reviewer identities exist; invitation expiry, suspension/revocation, 30-day device-token rotation, and break-glass access are exercised and reviewed.
- Jira OAuth uses an organization-owned Atlassian app and least-privilege projects; a test attachment and reconciliation exercise succeeded.
- Every required collector has complete pagination coverage and an approved least-privilege service identity.
- The legacy AWS collector uses a temporary STS access key, secret, and session token; a long-lived two-part key is rejected. Provider pagination cannot leave its original HTTPS origin.
- Repository SBOM generation uses either a fixed organization with a repository-restricted managed credential or short-lived one-time tokens; both have Metadata/Contents read only. Request-body logging is disabled, and a known-commit canary, independent review, and assessor-package inclusion test succeeded.
- Native Mac SBOM export was tested with a non-production repository; the URL/token dialog, immutable commit, bounded lockfile-only collection, CycloneDX/SPDX output, checksum, mode `0600`, token revocation, and documented manual review/retention path were verified.
- New Mac captures write to `~/Documents/Scopeproof Evidence`; Documents access, FileVault, backup, DLP, recovery, and synchronization policy are verified. Any legacy `~/Pictures/Scopeproof Evidence` artifacts remain inventoried until approved disposition.
- Native S3 production storage uses temporary credentials, a customer-managed KMS key, an enabled S3 Bucket Key for SSE-KMS, Object Lock, versioning, Block Public Access, BucketOwnerEnforced ownership, the exact transport/encryption/deletion-deny policy, a nonempty prefix, separate setup/daily/browser permissions, and tested CloudTrail/SNS alerts. The verified destination binding, upload receipt, exact-version recovery, download quarantine, replication, lifecycle, KMS recovery, and retention approvals were exercised where enabled.
- Backup verification and an isolated recovery drill met approved RPO/RTO.
- GitHub protected-branch checks, code-owner review, dependency updates, secret scanning, and release approvals are enabled.
- The production Mac build is Developer ID signed, hardened, notarized, stapled, update-signed, hosted on an approved HTTPS origin, and verified on a clean Mac.
- A representative current Mac completed schema-8 signed and deployment-matched capture → independent exact-pixel server scan → trusted RFC 3161 timestamp → final server chain linkage → independent review → scoped export → Jira disclosure test without manual database repair. Legacy and deliberately rebound/unbound fixtures remained quarantined.

If any item is not applicable, record the owner, rationale, compensating control, expiration date, and approval. An unchecked or undocumented item is not a production exception.
